---
title: Delegated credentials
description: "Give a machine a bounded way to use Executor without giving it a human account."
---

A **delegated credential** lets a machine use a small, explicit part of a human
account's Executor workspace. Executor keeps the grant separate from the
human session and checks it at every tool boundary. The machine does not
become the human, and it does not inherit the human's administrator role.

## The identities in a grant

Every grant keeps four identities distinct:

- the **creator** who starts or approves the grant
- the **machine actor** that presents the credential on each request
- the **effective subject** whose connections and membership are used
- the **grant** that fixes the consent and lifecycle

The effective subject must be a verified, currently enabled member. An
administrator may create a grant for another verified member when the host
allows that operation, but the grant still runs with the target member's
authority. The target member does not receive the creator's
administrator authority.

## Create and prove a credential

An Executor-issued key is shown once when it is created. Store it in the
machine's secret manager; Executor stores only the reference needed to resolve
the grant. Rotate or revoke the key when it may have been exposed.

An external credential, such as a Cloudflare Access service token, must first
complete a one-time possession challenge. The human starts the challenge and
gives the machine only the proof material it needs. Executor stores a digest
of the proof, never the bearer token or the service-token secret. The external
provider remains responsible for issuing and disabling that credential.

## Scope is a consent snapshot

Consent uses the account UI's toolkit and connection selections; callers do
not enter raw tool addresses or wildcards. Executor resolves those selections
to exact tool membership and stores an immutable scope snapshot. An omitted
connection limit means the frozen connections selected by the toolkit. An
explicit empty connection limit denies connection-backed calls. Adding a new
tool to an integration does not silently expand an existing grant.

Delegated requests may list a catalog, read a schema, invoke an approved tool,
and continue an approved execution or approval. Account administration,
credential management, grant management, and other management operations are
outside the delegated surface. Normal policies and connection ownership still
apply to every call.

## Expiry and revocation

Grants use the deployment's expiry policy: the default is 30 days and the
standard maximum is 90 days, with the operator able to configure a shorter
maximum.
Revoke a single grant when one machine is offboarded; use revoke-all when a
member leaves or all of that member's machines must stop. Revocation and
membership are checked again when a request, approval, or continuation is
handled. A known revoked or expired credential fails closed and is never
treated as an anonymous request.

Host operators control issuance and freshness with these settings. Durations
are integer milliseconds; the SDK hard maximum for a grant is 90 days.

| Host       | Issuance gate                                 | Maximum grant TTL                                                       | Recent human-auth window                                        |
| ---------- | --------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------- |
| Self-host  | `EXECUTOR_DELEGATED_CREDENTIAL_ISSUANCE=true` | `EXECUTOR_DELEGATED_MAX_TTL_MS` (default 90 days; hard maximum 90 days) | `EXECUTOR_DELEGATED_RECENT_AUTH_MAX_AGE_MS` (default 5 minutes) |
| Cloud      | `DELEGATED_ISSUANCE_ENABLED=true`             | `DELEGATED_MAX_TTL_MS` (default 90 days; hard maximum 90 days)          | `DELEGATED_RECENT_AUTH_MAX_AGE_MS` (default 5 minutes)          |
| Cloudflare | `DELEGATED_CREDENTIAL_ISSUANCE=true`          | `DELEGATED_MAX_TTL_MS` (default 90 days; hard maximum 90 days)          | `DELEGATED_RECENT_AUTH_MAX_AGE_MS` (default 5 minutes)          |

Leave each issuance gate unset or set to any value other than `true` until the
host's account and proof adapters are ready. Self-host and Cloudflare reject
malformed or over-limit TTL settings; Cloud's invalid or non-positive TTL value
falls back to the 90-day hard maximum. A shorter cap is useful during a canary.

Self-host measures recent human authentication from the Better Auth session
creation time. Cloud measures it from the signed administrator MFA proof. The
configured window applies to those host-specific assurance records, not to a
machine credential's age.

Cloudflare human management also requires a signed recent-login claim in the
verified Access JWT. The default claim is `auth_time`; configure
`DELEGATED_RECENT_AUTH_CLAIM` when the identity provider emits another signed
claim. The verifier accepts the claim at the JWT top level or inside Access's
signed `custom` object. It never treats `iat` as a login event. A missing or
stale claim fails closed.

Revoke-all normally revokes current grants while leaving the verified target
eligible for a later consent. An organization administrator can request
`disableTarget: true` when the host supports durable offboarding; the host then
marks the target unavailable after revocation commits. Hosts without that
offboarding callback reject the request, so removing a member from the host's
membership source remains the required fallback.

The audit record contains grant and credential references, subjects, action,
tool, outcome, and request or execution identifiers. It does not contain
tokens, authorization headers, tool arguments, or tool results.

## Account API naming

The source contract in this release keeps personal API keys at
`/account/api-keys`, with list, create, and revoke operations. Delegated
credentials use the separate `/account/delegated-credentials` surface; they do
not replace or reinterpret personal API keys.

## Roll out safely

Keep issuance disabled while the verifier, audit events, revocation checks, and
session binding are being verified. Enable issuance only in a local or
restricted canary with short-lived grants. Before broad rollout, exercise
allowed and denied tools, empty scopes, cross-tenant requests, administrator
non-inheritance, active-session revocation, and member offboarding.

To roll back, stop new issuance first, revoke affected grants, and block
delegated resolution while existing sessions are drained. Keep the grant
records and revocation tombstones available until no old session can present
them; removing the resolver must not turn a known credential into an absent
credential.
