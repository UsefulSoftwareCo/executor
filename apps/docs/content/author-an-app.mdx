An app is TypeScript source with a default `defineApp` export from the `apps`
package. A new app is two files: `index.ts` and a `package.json` that pins the
exact `apps` version the host runs:

```json
{ "name": "hello", "private": true, "type": "module", "dependencies": { "apps": "<version>" } }
```

Read that version from the host. Agents call the Executor app's
`framework.release`; the CLI prints it with `executor apps framework`. Create
the app with both files; a deploy without the version fails and names it.
To type-check outside Executor, install exactly that version with
`npm install --save-exact apps@<version>`. Do not install `apps@latest`: that
tag is separate from the Executor beta series.

Executor builds the app with the pinned package's server and browser framework.
It retains the compiled code with the version, so host updates do not replace
it. The exact version also keeps rebuilds on that version; a version range or
tag can select a newer version on the next build. Change it only to upgrade the
app. An unavailable or unsupported package fails the build and leaves the active
app unchanged. The host protocol is small and shared; early beta releases do not
promise indefinite support for every past version.

`defineApp` declares behavior and does not take a name. Set the package name
in `package.json`, such as `"name": "@team.executor.community/calendar"` when
publishing under the organization `team`. The name
you choose when creating or renaming an installed app is its editable display label.

Write ordinary async TypeScript. You do not import Effect and you do not import
the Executor SDK. The framework validates input and supplies the accounts each
call runs with.

## A first app

```ts
import { defineApp, object, query, router, string } from "apps";

const Greet = object({ name: string().default("world") });

export default defineApp(
  {},
  {
    tools: router({
      greet: query(
        { description: "Greet someone by name", input: Greet },
        async (_ctx, { name }) => ({ message: `Hello, ${name}!` }),
      ),
    }),
  },
);
```

`defineApp(requirements, definition)` takes what the app needs and what it
offers. `query(options, handler)` and `mutation(options, handler)` declare the
operations. Options are `description`, `input`, and optionally `output` and
`approval`. The `tools` router names them: this app has one tool, `greet`.
Nest routers to group tools; `router({ issues: router({ list, close }) })`
gives `issues.list` and `issues.close`.

The schema helpers are `object`, `string`, `number`, `boolean`, `array`,
`record`, `json` and `literal`. Use `.optional()` for a field that may be absent
and `.default(value)` for a default. `object` strips properties you did not
declare. `Infer<typeof Input>` gives you the parsed input type.

## Using an account

Declare a provider, require it, and read it off the context. A requirement
under `user` is filled by each caller's own linked account.

```ts
import {
  array,
  decodeJson,
  defineApp,
  defineProvider,
  object,
  query,
  type QueryContext,
  router,
  secrets,
  string,
} from "apps";

const vercel = defineProvider({
  name: "Vercel",
  auth: {
    apiKey: secrets({
      label: "API token",
      fields: object({ token: string({ minLength: 1 }) }),
    }),
  },
});

const requirements = { user: { accounts: { vercel } } };
type Context = QueryContext<typeof requirements>;

const Projects = object({ projects: array(object({ id: string(), name: string() })) });

const listProjects = query(
  { description: "List projects for the caller's Vercel account", input: object({}) },
  async (ctx: Context) => {
    const response = await ctx.fetch("https://api.vercel.com/v9/projects?limit=10", {
      headers: { Authorization: `Bearer ${ctx.user.accounts.vercel.fields.token}` },
    });
    return decodeJson(response, Projects);
  },
);

export default defineApp(requirements, { tools: router({ listProjects }) });
```

`ctx.user.accounts.vercel.fields` holds exactly the fields the method declared.
The token arrives per call, from the account the caller linked to the app.
Nothing in the source names an account, so the same code serves each member's
own account.

`decodeJson(response, schema)` checks the HTTP status and parses the body. Use
`oauth2({ discover: "..." })` instead of `secrets` for a browser sign-in; the
access token then arrives as `ctx.user.accounts.<name>.fields.access_token`.

For a requirement that takes several accounts, use `provider.many()`. The
context gives you a list.

### App accounts

Some accounts belong to the app rather than to whoever calls it: a team's
Datadog key, or one service account for an integration. Declare them under
`app`:

```ts
const requirements = {
  app: { accounts: { datadog } },
  user: { accounts: { github } },
};

async (ctx: MutationContext<typeof requirements>) => {
  ctx.app.accounts.datadog; // linked for everyone by people who can edit the app
  ctx.user.id; // the host's opaque caller identity, independent of linked accounts
  ctx.user.accounts.github; // the caller's own linked account
};
```

People who can edit an app link its app accounts, for everyone, on the app's
**Accounts** tab. Every caller, and the app's background work, uses the linked
account through the app, without access to the account itself. Callers never choose or replace it. A
requirement name is used once across `app` and `user`, and `.many()` works in
both.

A factory, `defineApp(requirements, async (ctx) => ...)`, is also evaluated
without a caller for the app's background work, so `ctx.user` may be undefined
there.

Apps written before `apps@0.0.1-beta.90` declared `{ accounts }` and read
`ctx.accounts`, which now fail. Every such requirement was a caller's account,
so it moves to `user`: `{ user: { accounts } }` and `ctx.user.accounts`. The
Executor app's `app-authoring` skill has the steps in
`upgrades/0.0.1-beta.90.md`. Nothing stored is converted: versions already
running keep their members' schedules. Deploying a schedule as `appCron` or
`appInterval` deletes the members' copies of it, with their settings, run
history and pending approvals, and the app schedule starts paused until an app
manager enables it.

### Caller identity

`ctx.user.id` identifies the caller in the host product. It is an opaque value
that stays the same across that person's calls, including calls to apps with
no account requirements. `ctx.user.accounts` still holds the caller's linked
accounts declared under `user: { accounts }`. The caller ID is independent of
those accounts and of the accounts linked for everyone under `app`.

Use the ID to attribute app records or enforce per-user limits. It is not an
account ID or an app owner, and grants no permissions. The host supplies it
after authentication; tool input cannot choose another caller.

In a factory, use `ctx.user?.id`: app-scoped background work evaluates the
factory without `ctx.user`. App-scoped handlers and workflow steps also have
no `ctx.user`. A host without user identities may leave `ctx.user.id` undefined
even in user scope; require an ID before relying on per-user attribution.

The app database and `ctx.cache` are shared by callers. Include the caller ID
in cache keys and filter stored rows when their contents belong to one caller.

## Queries and mutations

Both become tools. The difference is what they may do to the app's own stored
data.

- A query gets a read-only view.
- A mutation writes in a transaction that commits only after its output
  validates.

External calls are allowed from both, and external effects are never rolled
back.

## Approvals

Approval is declared on the operation.

```ts
import { mutation, object, string } from "apps";
import { always } from "apps/operations/approval";

const closeIssue = mutation(
  {
    description: "Close an issue",
    input: object({ id: string() }),
    approval: always(), // ask a person first; never() runs without asking
  },
  async (_ctx, { id }) => ({ closed: id }),
);
```

A function gets the real decision. It receives the tool name, the decoded input
and an abort signal, and returns `approved`, `denied` or `user-approval`.
Annotate a shared one with `Approval<Input>` to reuse it. For an operation
declared elsewhere, wrap it: `withApproval(operation, policy)`. For an imported
router, `withApprovals(router, (tool, name) => policy)` picks each tool's policy.

There is no app-level approval setting, and nothing is inferred from an
operation looking read-only. See
[Tools and approvals](/concepts/tools-and-approvals).

## Schedules and webhooks

A schedule runs a mutation on a timer, in one of two scopes:

```ts
import {
  appInterval,
  defineApp,
  mutation,
  type MutationContext,
  object,
  router,
  userCron,
} from "apps";

const requirements = {
  app: { accounts: { datadog } },
  user: { accounts: { github } },
};

// Runs as the app, without a caller, with the app's accounts only.
const sync = mutation(
  { input: object({}) },
  async (ctx: MutationContext<typeof requirements, "app">) => {
    await ctx.fetch("https://api.datadoghq.com/api/v1/validate", {
      headers: { "DD-API-KEY": ctx.app.accounts.datadog.fields.key },
    });
    return null;
  },
);

// Runs as each member who enables it, with their linked accounts.
const digest = mutation(
  { input: object({}) },
  async (ctx: MutationContext<typeof requirements>) => {
    await ctx.fetch("https://api.github.com/notifications", {
      headers: { Authorization: `Bearer ${ctx.user.accounts.github.fields.token}` },
    });
    return null;
  },
);

export default defineApp(requirements, {
  tools: router({ sync, digest }),
  schedules: {
    sync: appInterval({ minutes: 15 }, sync, {}),
    digest: userCron({ expression: "0 9 * * MON-FRI", timezone: "America/Los_Angeles" }, digest, {}),
  },
});
```

`appInterval` and `appCron` declare one schedule, which an app manager enables
and which runs with the app's accounts. `userInterval` and `userCron` give each
member their own copy, which they enable and which runs as them. Schedules start
paused. A context of the `"app"` scope, `MutationContext<typeof requirements, "app">`,
has no `user`; app schedules take only such mutations, or ones whose handler
declares no parameters, and only ones without an `approval`, because no person
is there to ask. A handler that declares its context without a type gets the
caller's, with `ctx.user`, so a tool can read the caller's accounts; give it the
`"app"` scope's type to schedule it as the app. With explicit type arguments,
`mutation<Input, Output>(…)` gets the caller's context even when its handler
declares no parameters; pass the `"app"` scope's context as the third.

A webhook names the requirement whose account is its source:
`account: { user: "github" }` registers it for each linked GitHub account, and
`account: { app: "datadog" }` for the account linked for everyone, without a caller.
A webhook written inline in `defineApp` states its context, so its handlers are
typed: `satisfies Webhook<WebhookContext<typeof requirements, "app">, Config, State>`.

## Asking for input mid-tool

```ts
import { object, query } from "apps";

const nameResult = query(
  { description: "Ask for a name", input: object({}) },
  async (ctx) => {
    const answer = await ctx.elicit({
      mode: "form",
      message: "Name this result",
      requestedSchema: {
        type: "object",
        properties: { name: { type: "string" } },
        required: ["name"],
      },
    });
    return answer.action === "accept" ? { ...answer.content } : {};
  },
);
```

The question reaches the person the same way an approval does. The answer's
`action` is `accept`, `decline` or `cancel`; only an accepted answer carries
`content`, the submitted fields.

## Importing an existing service

You do not have to write handlers to wrap an API.

```ts
import { defineApp } from "apps";
import { mcpRouter } from "apps/mcp";

export default defineApp({}, async ({ signal }) => ({
  tools: await mcpRouter({
    url: "https://mcp.deepwiki.com/mcp",
    signal,
  }),
}));
```

The helpers are `mcpRouter` from `apps/mcp`, `graphqlRouter` from
`apps/graphql` and `liveOpenapiRouter` from `apps/openapi`. Each returns a router. Use it as `tools`, or mount several
under keys, such as `tools: router({ docs: await mcpRouter(...) })`, which
names their tools `docs.<tool>`. An operation that cannot be classified
becomes a mutation. `mcpRouter` needs `@modelcontextprotocol/sdk` in the
app's `package.json` dependencies, and `graphqlRouter` needs `graphql`.

The dashboard's **Custom app** form does the same thing from a URL, for MCP,
GraphQL and OpenAPI, without writing any source.

## Storing data

Add SQL files to `migrations/` and the app gets its own SQLite database. The
host applies new ones in number order when you deploy. A failing migration fails
the deploy with SQLite's error, and applied migrations cannot be edited: add a
new one instead.

```sql
-- migrations/0001_messages.sql
CREATE TABLE messages (
  id TEXT PRIMARY KEY NOT NULL,
  mailbox TEXT NOT NULL,
  subject TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX messages_mailbox ON messages (mailbox, created_at);
```

Handlers read and write through `ctx.sql`, with `?` for values:

```ts
import {
  defineApp,
  mutation,
  type MutationContext,
  object,
  query,
  type QueryContext,
  router,
  string,
} from "apps";

const requirements = {};
type Message = { id: string; subject: string };

const list = query(
  { description: "Recent messages", input: object({ mailbox: string() }) },
  async ({ sql }: QueryContext<typeof requirements>, { mailbox }) =>
    sql
      .exec<Message>(
        "SELECT id, subject FROM messages WHERE mailbox = ? ORDER BY created_at DESC LIMIT 50",
        mailbox,
      )
      .toArray(),
);

const add = mutation(
  { description: "Store a message", input: object({ mailbox: string(), subject: string() }) },
  async ({ sql }: MutationContext<typeof requirements>, message) =>
    sql
      .exec<Message>(
        "INSERT INTO messages (id, mailbox, subject, created_at) VALUES (?, ?, ?, ?) RETURNING id, subject",
        crypto.randomUUID(),
        message.mailbox,
        message.subject,
        Date.now(),
      )
      .one(),
);

export default defineApp(requirements, { tools: router({ list, add }) });
```

`exec<Row>` types the rows it returns. Queries get read-only SQL; mutations can
write. Each statement commits on its own, and `ctx.sql.transaction(...)` groups statements. A transaction is
synchronous, so calls to other services always happen between transactions,
never inside one.

## Shipping instructions

An app can carry its own guidance for agents. Put it beside the source:

<FileTree>

- index.ts
- skills/
  - triage/
    - SKILL.md
    - references/
      - examples.md

</FileTree>

```md
---
name: triage
description: Search cached messages before fetching more history.
---

Read [examples](references/examples.md), then discover this app's tools.
```

An agent reads it with the `skills` tool. Skill text never grants a permission;
the approval still decides.

## Deploying

Deploying is an operation, not a command. Have your agent call it through the
MCP endpoint. Read the version with `framework.release`, create the app from
`index.ts` and the `package.json` that pins it, then deploy the same files:

<CodeGroup>

```js Hosted
const executor = tools.executor;
const path = { organization: "<approved-organization-id>" };
const { version } = await executor.framework.release({ path });
const files = [
  { path: "index.ts", content: "<contents of index.ts>" },
  {
    path: "package.json",
    content: JSON.stringify({
      name: "hello",
      private: true,
      type: "module",
      dependencies: { apps: version },
    }),
  },
];
const app = await executor.appManagement.create({ path, body: { name: "Hello", files } });
return await executor.appManagement.deploy({ path: { ...path, app: app.id }, body: { files } });
```

```js Local
const executor = tools.executor;
const { version } = await executor.framework.release({});
const files = [
  { path: "index.ts", content: "<contents of index.ts>" },
  {
    path: "package.json",
    content: JSON.stringify({
      name: "hello",
      private: true,
      type: "module",
      dependencies: { apps: version },
    }),
  },
];
const app = await executor.appManagement.create({ body: { name: "Hello", files } });
return await executor.appManagement.deploy({ path: { app: app.id }, body: { files } });
```

</CodeGroup>

From a shell, write the same two files into a directory, using the version
`executor apps framework` prints:

```sh
executor apps create --name "Hello" --files ./hello    # prints the app, including its id
executor apps source --app <app-id> | jq -r .revision.commit
executor apps deploy --app <app-id> --commit <first-commit>
```

The app activates only after the build succeeds, and earlier versions are
retained; see [Apps and versions](/concepts/apps-and-versions). Then
connect an account for each requirement and, in a new `execute`, call the path
`tools.search` returns. An app without accounts is called by its slug:

```js
return await tools.hello.greet({ name: "Ada" });
```

An app with accounts is called the same way. Each call uses the accounts you
linked to the app; there is no account input. To use another account, link it
on the app's **Accounts** tab, which replaces the one before for a
single-account requirement.

### Updating an existing app

Create-by-name calls reject an existing name. Edit an existing app through the
same source, commit and deploy operations on Local and Hosted. Read their current
signatures first. Hosted paths include `organization`; Local paths contain only
`app`.

```js
const executor = tools.executor;
const path = { organization: "<approved-organization-id>", app: "<app-id>" };
const source = await executor.appManagement.source({ path });
const files = source.files.map((file) =>
  file.path === "index.ts" ? { ...file, content: "<complete updated source>" } : file,
);
const saved = await executor.appManagement.commit({
  path,
  body: { expected: source.revision.commit, message: "Update greeting", files },
});
if (saved.removed.count > 0) {
  throw new Error(`The save removed ${saved.removed.count} files: ${saved.removed.paths.join(", ")}`);
}
return await executor.appManagement.deploy({
  path,
  body: { commit: saved.revision.commit },
});
```

The commit replaces the complete file list, so keep `package.json` in it.
Its result's `removed` gives the `count` of files it deleted and at most 100
of their `paths`; check it before deploying. A deleted file is still in `source.files`
and in the `expected` commit, so add it back and commit again to keep it. A
path cannot be both a file and a folder; such a save fails with
`SourcePathConflict` and saves nothing.
Saving source does not deploy it.
Web pages show source; agents or ordinary Git clients edit it.

Discovery is not cached across a change, so run `tools.search` again after you
deploy.

The CLI also provides `executor apps source`, `executor apps commit`,
`executor apps deploy --commit <sha>` and `executor apps deploy --files <dir>`.
Deploying reads the chosen commit and leaves the Git branch unchanged. Ordinary
Git pushes save source without deploying it.

Code, every file outside `ui/public/`, is UTF-8 text: at most 4,096 files and
16 MiB of file contents. Files under `ui/public/` are served as they are and may
be binary, such as images, fonts, audio and WebAssembly: at most 10,000 files,
each at most 32 MB and 1 GB in total. Builds never load them; each deploy copies
them to the host's storage and serves them from there. The CLI checks a directory
or JSON file against these limits before uploading it and names the files that
are too large, or binary outside `ui/public/`. A directory over 16 MiB in total
is pushed with Git, in several pushes when it is large. Source reads list binary
public files as `{ "path", "object", "size" }`; send them back unchanged to keep
them, or clone the app to get their bytes. A failed CLI command prints the
host's error code, HTTP status, message and recovery; when its output is not a
terminal it also prints them as `{ "error": ... }` JSON on standard output.
When a newer CLI release exists, the failure also says so and how to update.

## Update a hosted app

Use `appManagement.deploy` with `{ files: [...] }` to deploy a complete file set,
or `{ commit: "<sha>" }` to deploy an existing Git commit. Deploying files does not
save changes to Git. The app keeps its ID and stored data. The newest successful
version becomes active. Use `apps.activate` to select a retained version;
activation does not roll back stored data.

## Open an app UI

React is the only supported app UI framework for now. Include `ui/index.html`,
a React entry such as `ui/main.tsx`, and styles in the app's files. Declare
`react` and `react-dom` in the app's package dependencies. The host builds and
activates the browser assets with the server code. No separate publish step is
needed. SSR and React Server Components are not supported yet.

You can bring your own React components or browser-compatible npm component
libraries. Declare their dependencies and include the required styles and
assets. Libraries that need custom build plugins require additional build
support.

Tailwind CSS v4 compilation is built in. Import a stylesheet from your React
entry:

```tsx
import "./style.css";
```

Start `ui/style.css` with:

```css
@import "tailwindcss";
```

Write complete utility classes in your React components. No Tailwind dependency,
config file or separate build command is needed. The build scans browser code,
including imported components and lazy chunks. Ordinary CSS and component-library
styles can share the same app.

Use CSS `@theme` for custom tokens. Use `@source inline("...")` to include classes
that only arrive at runtime. Filesystem `@source` paths and JavaScript `@config`
or `@plugin` files are not supported.

For hosted apps, discover `appUi.location` through `tools.search` and call it:

```js
return await tools.executor.appUi.location({
  path: { organization: "<approved-organization-id>", app: "<app-id>" },
});
```

Open the returned `url` in a browser. Executor Cloud uses
`https://<app-slug>.<org-slug>.executor.website`; self-host uses its configured
app domain. Use the returned URL instead of guessing it. A null URL with
`status: "unavailable"` gives a `reason`: `"no_ui"` when the app has no UI, or
`"no_app_domain"` when the host has no app domain configured.

App pages are private. Opening the link starts browser sign-in through Executor.
A successful tool call or a `403` from a guessed address does not verify that
the UI renders. Check the actual page before reporting it as working.
