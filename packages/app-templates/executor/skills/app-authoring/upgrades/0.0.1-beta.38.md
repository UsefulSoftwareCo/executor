# Upgrade to apps@0.0.1-beta.38

This release replaces the document database (`defineDatabase`, `table`,
`ctx.db`) with SQL through `ctx.sql`. Apps without a database only bump the
version. Deployments you already have keep running unchanged until you deploy
again.

## 1. Bump the version

Set `"apps": "0.0.1-beta.38"` in `package.json`.

## 2. Remove the database declaration

```ts
// Before
const requirements = {
  accounts: { github },
  database: defineDatabase({
    notes: table({ text: string(), pinned: boolean() }).index("by_pinned", ["pinned"]),
  }),
};

// After
const requirements = { accounts: { github } };
```

Remove the `defineDatabase`, `table`, `id` and `userId` imports. The app has a
database because it has migrations; there is nothing to declare.

## 3. Create the tables, and copy the old rows

Write `migrations/0001_init.sql`. The document API stored every row as JSON in
`_executor_legacy_rows (table_name, id, body)`, with `createdAt` and `updatedAt`
inside the body. Copy them into the new tables in the same migration:

```sql
CREATE TABLE notes (
  id TEXT PRIMARY KEY NOT NULL,
  text TEXT NOT NULL,
  pinned INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL
);
CREATE INDEX notes_pinned ON notes (pinned, created_at);
INSERT INTO notes (id, text, pinned, created_at)
SELECT
  id,
  json_extract(body, '$.text'),
  coalesce(json_extract(body, '$.pinned'), 0),
  json_extract(body, '$.createdAt')
FROM _executor_legacy_rows
WHERE table_name = 'notes';
```

`_executor_legacy_rows` exists in every app database and is empty when the app
never stored rows, so the same migration works for a fresh deploy or a copy of
the app. Booleans are stored as JSON `true`/`false`; `json_extract` returns them
as `1`/`0`. Check `createdAt`'s format in a few rows before relying on it, for
example with a query running `SELECT body FROM _executor_legacy_rows LIMIT 5`.

The old tables stay in the database untouched. Nothing is deleted.

## 4. Rewrite handlers

`ctx.sql` is synchronous, so drop the `await`s.

```ts
// insert(value)
ctx.sql
  .exec(
    "INSERT INTO notes (id, text, created_at) VALUES (?, ?, ?) RETURNING *",
    crypto.randomUUID(),
    text,
    Date.now(),
  )
  .one();
// get(id)
ctx.sql.exec("SELECT * FROM notes WHERE id = ?", id).toArray()[0] ?? null;
// update(id, patch)
ctx.sql.exec("UPDATE notes SET pinned = 1 WHERE id = ?", id);
// delete(id)
ctx.sql.exec("DELETE FROM notes WHERE id = ? RETURNING id", id).toArray().length > 0;
// withIndex("by_pinned", (q) => q.eq("pinned", true)).take(20)
ctx.sql.exec("SELECT * FROM notes WHERE pinned = 1 ORDER BY created_at LIMIT 20").toArray();
// count()
ctx.sql.exec("SELECT count(*) AS n FROM notes").one().n;
// paginate({ cursor, numItems }): pass the last row's created_at as the next cursor
ctx.sql
  .exec("SELECT * FROM notes WHERE created_at < ? ORDER BY created_at DESC LIMIT ?", cursor, size)
  .toArray();
```

Rows come back with your column names, so rename `createdAt` to `created_at`
in callers or alias it (`created_at AS createdAt`). Nothing adds `id`,
`createdAt` or `updatedAt` for you; write them yourself.

The document API's per-call row budgets are gone, so `DatabaseLimitExceeded`
no longer occurs. Keep batching large work, since a long statement holds the
database for every other call.

## 5. Revisit mutations that call other services

A mutation used to be one transaction, so a failed `fetch` after an insert
rolled the insert back. Now each statement commits on its own, and
`ctx.sql.transaction(() => ...)` groups statements but cannot contain an
`await`. Where a mutation writes, calls a service, then writes again, use the
reserve, call, publish pattern in [storage.md](../storage.md), and handle the
row a failure leaves behind. Writes that two calls can race on should be
conditional (`UPDATE ... WHERE status = 'pending'`) and check `rowsWritten`.

## 6. Workflow step mutations

A mutation run with `step.runMutation` writes only inside one
`ctx.sql.transaction(...)`. That transaction also records the step's receipt, so
a retried step never writes twice. A write outside it fails, and so does a
second transaction in the same step.

```ts
const save = mutation({ input }, async (ctx, input) =>
  ctx.sql.transaction((tx) =>
    tx
      .exec(
        "INSERT INTO reports (id, repository) VALUES (?, ?) RETURNING id",
        crypto.randomUUID(),
        input.repository,
      )
      .one(),
  ),
);
```

## 7. Deploy

Deploy as usual. The host applies `migrations/` before activating the new
version. If a migration fails, the deploy fails with the migration's name and
the previous version keeps running.
