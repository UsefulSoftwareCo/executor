# Upgrade to apps@0.0.1-beta.90

This release declares account requirements by scope. `user` requirements are
each caller's own linked accounts, as every requirement was before. `app`
requirements are new: accounts linked for everyone by people who can edit the
app, which every caller and the app's background work use. `{ accounts }` requirements, `ctx.accounts`,
`cron` and `interval` are removed, and source that uses them fails to build.
Deployments you already have keep running unchanged until you deploy again.
Existing links stay user links, and members' schedule copies stay theirs while
their declarations stay user schedules.

## 1. Bump the version

Set `"apps": "0.0.1-beta.90"` in `package.json`.

## 2. Move requirements to `user`

<!-- app-user-accounts: keep -->

```ts
// Before
const requirements = { accounts: { github } };
// After
const requirements = { user: { accounts: { github } } };
```

An app without accounts declares nothing: `{ accounts: {} }` becomes `{}`.

## 3. Read the caller's accounts from `ctx.user`

```ts
// Before
ctx.accounts.github.fields.token;
async ({ accounts, fetch }) => accounts.github.id;
// After
ctx.user.accounts.github.fields.token;
async ({ user, fetch }) => user.accounts.github.id;
```

Workflow steps change the same way: `step.accounts` becomes
`step.user.accounts`. A factory, `defineApp(requirements, async (ctx) => ...)`,
also runs without a caller for app-scope work, so `ctx.user` may be undefined
there: write `ctx.user?.accounts.service ?? []` for a `.many()` requirement,
or return no tools without a caller.

## 4. Name the scope of a webhook's account

```ts
// Before
account: "github",
// After
account: { user: "github" },
```

## 5. Choose each schedule's scope

`cron` and `interval` become `userCron` and `userInterval` when the app has user
requirements: each member enables their own copy, which runs as them, as before.

An app without user requirements uses `appCron` and `appInterval`: one schedule,
which an app manager enables and which runs without a caller. Its mutation
declares no `approval`, and its handler either declares no parameters or takes
`MutationContext<typeof requirements, "app">`. A context declared without a type
is the caller's, so `async (ctx) => …` needs that type; the codemod adds it. So
does `mutation<Input, Output>(…)` with explicit type arguments, even without
parameters; the codemod adds it as the third type argument. Keep `userCron` or `userInterval`
for a mutation that asks for approval, or to keep one copy per member.

Nothing stored is converted. The deployment already running keeps its members'
schedule copies. Deploying a declaration as an app schedule deletes those copies,
with their settings, run history and pending approvals, and the app schedule
starts paused until an app manager enables it. The codemod warns at each schedule
it makes an app schedule.

```ts
const tick = mutation(
  { input: object({}) },
  async (ctx: MutationContext<typeof requirements, "app">) => ctx.sql.exec("...").toArray(),
);
export default defineApp(requirements, {
  tools: router({ tick }),
  schedules: { tick: appInterval({ minutes: 5 }, tick, {}) },
});
```

## 6. Optionally, give the app its own accounts

A requirement every caller should share, such as a team's service key, can move
to `app: { accounts: { ... } }` and be read as `ctx.app.accounts`. Its members'
existing links do not carry over: someone who can edit the app links an account
for everyone on the app's Accounts tab after you deploy. See [accounts.md](../accounts.md).

## 7. Deploy

Deploy as usual and check the build output for the removed names.
